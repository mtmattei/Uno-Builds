The big idea: two MCPs that close the loop

Visual parity is the goal of making the running application look like the design — not "close enough in code," but verified against a real, rendered screenshot of the real app on the real platform.

This is hard for an LLM alone because a model writing XAML works blind: it emits markup and hopes it renders. Uno Platform closes that loop with two complementary MCP servers, so the agent can see what it built and correct itself.

Server 01 · Remote

Uno MCP

https://mcp.platform.uno/v1

Semantic search & fetch over Uno docs, APIs, and best-practice guidance, plus "priming" prompts that teach the agent how Uno apps are structured. Keeps the code correct and idiomatic.

Server 02 · Local

App MCP

Uno Dev Server → running app

A live handle on the running app: screenshots, visual-tree snapshots, input simulation, and lifecycle control. Keeps the code visually accurate.

Neither alone gets you there. Together they produce an app that both looks right and follows best practices — the same way a developer alt-tabs between the design and the running app, but automated.

Prerequisites

  • .NET SDK with the Uno workload — dotnet workload install uno, or validate with uno check.
  • Claude Code (CLI or IDE extension). The same flow works for VS Code Copilot, Codex, Cursor — only the mcp install <client> argument changes.
  • A desktop target you can run locally (Windows or Skia Desktop) — the fastest inner loop for the App MCP to attach to.
  • The target design as an image file.
💡

Why local? The App MCP talks to a running process on your machine. Screenshots and visual-tree snapshots need an actual rendered app, so this loop runs on a developer machine, not a headless sandbox.

01Wire up the two MCPs in Claude Code

The Uno Dev Server ships a one-command installer that registers both MCP entries using your agent's native config format. For Claude Code it delegates to claude mcp add --scope project, landing them in the project's .mcp.json.

bash — project root
# Installs the Uno MCP + App MCP entries for Claude Code
uno-devserver mcp install claude-code

# No global tool installed? Run it transiently via dnx:
dotnet dnx -y uno.devserver mcp install claude-code

# Verify: shows detected clients, config path, transport, variant
uno-devserver mcp status

02Give the agent the target design

Drop the image into the conversation and state the intent plainly — be explicit that parity is verified with the App MCP, not assumed.

You →

Here is the target design — the JurSpace legal dashboard. Build this as an Uno page. Work in a loop: after each change, use uno_app_get_screenshot to capture the running app, compare it against the design, and keep refining until they match. Use the Uno docs MCP to choose idiomatic controls and layouts, and follow best practices (theme resources, responsive layout, MVUX).

Have the agent read the design out loud first — it forces an explicit inventory before any code, and gives you a checklist to verify against:

  • App bar: logo + wordmark, phone, email, a "back to main" link, language/globe icon, hamburger menu.
  • Greeting: a localized welcome + culture-aware date ("Пятница, 3 апреля 2026").
  • Card grid (responsive): leads with count badges · active cases with status pills срочноев работеожидание · messages with unread counts.
  • Stat tiles: "2 documents to sign" (navy), "4 tasks today" (blue).
  • Calendar: a month grid with prev/next and highlighted days (navy + teal).
  • Useful links: pill-shaped chips.

05The visual-parity loop

The heart of the workflow. Each iteration is edit → screenshot → compare → diagnose → fix. Do it in slices — structure, then components, then polish — so each screenshot isolates one kind of change.

One turn of the loop
1
Read the designInventory regions, components, colors, type.
2
Ask the Uno MCP“How should I structure this?” → uno_platform_docs_search
3
Write / edit XAML + view modelsIdiomatic markup, bound to data.
4
See the resultCapture the running app → uno_app_get_screenshot
5
Compare screenshot ⇄ designList every visible difference.
6
Diagnose structurallyInspect resolved layout → uno_app_visualtree_snapshot
7
Best-practice fixCorrect via theme resources / bindings, then loop.
↻ repeat 3–7 until the screenshot matches the design

Iteration 1 — Page skeleton

You →

Lay out the top-level structure only: an app-bar row, a greeting row, and a responsive content grid with placeholders for each card region. Then uno_app_get_screenshot and compare the proportions and regions to the target — ignore colors and content for now.

When placement is wrong (a common first-pass error is cards stacking instead of gridding), have the agent diagnose structurally rather than guess:

You →

The right column isn't aligning. Call uno_app_visualtree_snapshot and tell me the actual Grid.Row/Grid.Column and sizes each region resolved to versus what you intended.

The snapshot is text, so the agent reasons about actual resolved layout instead of re-reading its own XAML. That's what makes the correction reliable.

06Layer in best practices

Parity is necessary but not sufficient — the point of the two MCPs is to reach parity with clean code. Have the agent verify each item against the Uno docs MCP.

Theme resources

Colors, brushes, radii, and text styles live in resource dictionaries — never inline literals. Override the Material palette the documented way.

Responsive layout

Use VisualStateManager / AdaptiveTrigger so the grid reflows to one column on narrow widths. Screenshot at two sizes to prove it.

MVUX / MVVM

Greeting, lists, badges, and calendar bind to a model — not code-behind. That's what makes the counts real.

Localization

Strings live in Strings/*/Resources.resw; the date uses culture-aware formatting.

Accessibility

Automation names on icon buttons; sufficient contrast on status pills. Verify reachability via the visual-tree snapshot.

Data-driven

Item templates over copy-paste rows, so lists stay maintainable and bindable.

MCP tool reference

Uno MCP — remote docs server

ToolPurpose
uno_platform_docs_searchSemantic search across Uno docs, APIs, guides.
uno_platform_docs_fetchRetrieve a specific document (markdown, with code).
uno_platform_agent_rules_initPrime the agent on how to build Uno apps.
uno_platform_usage_rules_initPrime the agent on API best practices.

App MCP — local dev-server server

ToolPurpose
uno_healthDev Server health / connection status.
uno_app_get_runtime_infoApp PID, OS, platform info.
uno_app_get_screenshotCapture a screenshot of the running app.
uno_app_visualtree_snapshotTextual snapshot of the live visual tree.
uno_app_pointer_clickClick at (X, Y).
uno_app_key_pressPress keys with modifiers.
uno_app_type_textType a text string.
uno_app_element_peer_default_actionInvoke an element's default action.
uno_app_start / uno_app_closeManage app lifecycle.
uno_app_element_peer_actionPROInvoke a specific automation-peer action.
uno_app_get_element_datacontextPRORead an element's DataContext.
ℹ️

Tool availability depends on your Uno license tier (Community vs. Pro). Names reflect the Uno Dev Server MCP at time of writing — run /mcp in Claude Code to see the exact set for your version.

Sample best-practice XAML

Illustrative snippets the agent should converge on — data-driven, resource-themed, responsive — not hand-copied rows with inline colors.

Theme resources, not inline literals

Styles/ColorPaletteOverride.xaml
<ResourceDictionary xmlns="...presentation" xmlns:x="...xaml">
  <!-- JurSpace palette -->
  <Color x:Key="BrandBlue">#2F6BFF</Color>
  <Color x:Key="BrandNavy">#0B1F5B</Color>
  <Color x:Key="BrandTeal">#12B886</Color>

  <!-- Status pills -->
  <SolidColorBrush x:Key="StatusUrgentBrush" Color="#F28B82"/>
  <SolidColorBrush x:Key="StatusInWorkBrush" Color="#7FD99A"/>
  <SolidColorBrush x:Key="StatusWaitingBrush" Color="#F5D547"/>

  <!-- Reusable card style -->
  <Style x:Key="DashboardCard" TargetType="Border">
    <Setter Property="CornerRadius" Value="20"/>
    <Setter Property="Padding" Value="28"/>
  </Style>
</ResourceDictionary>

Responsive grid with AdaptiveTrigger

MainPage.xaml
<Grid x:Name="ContentGrid" ColumnSpacing="24" RowSpacing="24">
  <Grid.ColumnDefinitions>
    <ColumnDefinition Width="*"/>
    <ColumnDefinition Width="*"/>
  </Grid.ColumnDefinitions>

  <VisualStateManager.VisualStateGroups>
    <VisualStateGroup>
      <VisualState>
        <VisualState.StateTriggers>
          <AdaptiveTrigger MinWindowWidth="0"/>
        </VisualState.StateTriggers>
        <VisualState.Setters>
          <!-- collapse to one column on narrow screens -->
          <Setter Target="ContentGrid.(Grid.ColumnDefinitions)[1].Width" Value="0"/>
        </VisualState.Setters>
      </VisualState>
      <VisualState>
        <VisualState.StateTriggers>
          <AdaptiveTrigger MinWindowWidth="900"/>
        </VisualState.StateTriggers>
      </VisualState>
    </VisualStateGroup>
  </VisualStateManager.VisualStateGroups>
</Grid>

Data-driven "Active cases" card

MainPage.xaml — bind, don't copy
<Border Style="{StaticResource DashboardCard}">
  <StackPanel Spacing="16">
    <TextBlock Text="Активные дела" Style="{StaticResource TitleTextBlockStyle}"/>

    <ItemsControl ItemsSource="{Binding ActiveCases}">
      <ItemsControl.ItemTemplate>
        <DataTemplate>
          <Grid Padding="0,12" ColumnSpacing="12">
            <StackPanel>
              <TextBlock Text="{Binding Title}"/>
              <TextBlock Text="{Binding Assignee}" Opacity="0.6"/>
            </StackPanel>
            <!-- converter maps status -> brush resource -->
            <Border CornerRadius="12" Padding="12,4"
                    Background="{Binding Status, Converter={StaticResource StatusToBrush}}">
              <TextBlock Text="{Binding StatusLabel}"/>
            </Border>
          </Grid>
        </DataTemplate>
      </ItemsControl.ItemTemplate>
    </ItemsControl>
  </StackPanel>
</Border>

The agent reaches code like this because the Uno MCP told it to (resource theming, adaptive triggers, data binding are all in the docs) and confirms it looks right because the App MCP screenshotted it. That's visual parity with best practices — the whole point.
